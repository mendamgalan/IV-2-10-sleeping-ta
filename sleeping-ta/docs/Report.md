# The Sleeping Teaching Assistant — тайлан

IV-2-10 · F.CSM302 Үйлдлийн систем · Бие даалт 1 · хувилбар 1.1 (2026-11-13)

## Хураангуй

Operating System Concepts-ийн 7-р бүлгийн Project 2 “The Sleeping Teaching Assistant”-ийг C хэл
дээр POSIX thread, mutex, semaphore ашиглан хэрэгжүүлэв. TA болон 1–40 оюутан тус бүр тусдаа
thread. Сул TA semaphore дээр унтаж, ирсэн оюутан түүнийг сэрээнэ; TA завгүй бол оюутан 0–20
сандлын нэг дээр FIFO дарааллаар хүлээж, сандал дүүрэн бол программчилж байгаад дахин ирнэ.
Номын `sleep()`-ийн оронд 100 мс-ийн загварын цаг хэрэглэснээр Tkinter цонхоос туршилтыг
зогсоох, алхамчлах, seed-ээр яг давтах боломжтой болсон; “чөлөөт горим” нь оюутнуудыг нэг
tick дотор бодитоор зэрэг ажиллуулж синхрончлолыг шалгана.

Хувилбар 1.1 нь дотоод шүүмжийн 12 асуудлыг засав. 26 Python тест, 2 C тест, ThreadSanitizer
бүгд амжилттай. Гол үр дүн: (1) чөлөөт горимд 15 000 tick-д дүрэм зөрчигдөөгүй, mutex-ийг
авбал TSan race илрүүлж дүрэм эхний tick-д эвдэрнэ; (2) тусламжийн хуваарилалтын алдааг
засаж, урт туршилтад тусламж авсан оюутан 40-өөс 4 байсныг 37 болгов; (3) сандлын тоо
нэмэгдэхэд буцалт 65.9 %-иас 0 % хүртэл буурч, дундаж хүлээлт 0-ээс 4.95 с хүртэл өсдөг.

## 1. Удиртгал

Олон thread нэг нөөцийг (энд нэг TA, хязгаартай сандал) хуваалцахад зохицуулалт хэрэгтэй:
хамтын өгөгдөлд зэрэг хандвал race condition, буруу дарааллаар хүлээвэл deadlock, зарим thread
хэзээ ч нөөц авахгүй байвал starvation үүснэ. Sleeping TA бол эдгээрийг жижиг хэмжээнд
харуулдаг сонгодог бодлого. Төслийн зорилго: (1) номын шаардлагыг бодит thread, mutex,
semaphore-оор хэрэгжүүлэх, (2) оюутны тоо, сандал, хугацааг сольж туршиж болох интерактив UI
хийх, (3) зөв ажиллагааг тест болон тоон туршилтаар нотлох. Хамрах хүрээ: нэг TA, 1–40
оюутан, 0–20 сандал. CPU scheduler-ийн гүйцэтгэл хэмжих зорилгогүй.

## 3. Онолын үндэс

**Thread ба race condition.** Нэг процессын thread-үүд санах ойг хуваалцана. Хоёр thread нэг
хувьсагчийг зохицуулалтгүй уншиж, өөрчилбөл үр дүн гүйцэтгэлийн дарааллаас хамаарна. Энд
хамтын өгөгдөл нь дараалал (`queue`, `waiting_count`), TA-ийн төлөв (`current`, `remaining`),
оюутны төлөв, тоолуур, санамсаргүй тооны төлөв.

**Mutex.** `pthread_mutex_t mu` нь дээрх өгөгдлийг өөрчлөх хэсэгт нэг thread л нэвтрэхийг
баталгаажуулна. Жишээ нь хоёр оюутан зэрэг ирээд сүүлийн нэг сандлыг хоёулаа авах race-ийг
хаана.

**Semaphore.** Тоологч бүхий дохио: `sem_wait` тоолуур 0 үед thread-ийг блоклож, `sem_post`
нэмэгдүүлж хүлээж буй thread-ийг сэрээнэ. Энэ нь “унтах/сэрэх”-ийг busy-wait-гүйгээр
хэрэгжүүлнэ: сул TA, сандал дээрх оюутан, тусламж авч буй оюутан CPU хэрэглэхгүй хүлээнэ.

**Deadlock-оос сэргийлэх.** Thread semaphore дээр хүлээхээсээ өмнө mutex-ээ суллана. Mutex
барьсаар хүлээвэл дохио өгөх ёстой thread mutex авч чадахгүй гацна.

**FIFO ба шударга байдал.** Сандал дээр суусан оюутныг ирсэн дарааллаар нь дуудна. Сандалгүй
буцсан оюутанд тодорхой хугацаанд тусламж авах баталгаа номын шийдэлд ч байхгүй; хэн дараа нь
түрүүлж ирэхийг OS scheduler шийднэ. Тиймээс загвар нь оюутнуудын дарааллыг тогтмол биш,
санамсаргүй байлгах ёстой (5.3, 8.3).

## 4. Системийн зохиомж

Өгөгдлийн урсгал: **Tkinter (`app.py`) → `model.py` (ctypes) → `libta.so` (`engine.c`) → TA
ба n оюутны thread**. Буцах урсгал: C snapshot (JSON) → UI. UI дараалал, тусламжийн үр дүнг
өөрөө тооцохгүй, зөвхөн хөдөлгүүрийн төлөвийг зурна.

| Файл | Үүрэг |
|---|---|
| `src/engine.c` | Thread, mutex, semaphore, FIFO, загварын цаг, журнал, экспорт |
| `src/model.py` | ctypes интерфейс, оролт шалгах, CSV-г аюулгүй солих |
| `src/app.py` | Тохиргоо, удирдлага, дүрслэл, бодит цагтай автомат горим |
| `tests/` | Хөдөлгүүр, regression, UI, нөөцийн алдаа, чөлөөт горимын stress тест |
| `docs/experiments.py` | 8-р хэсгийн туршилт ба график |

| Semaphore | Хэн хүлээнэ | Хэн дохио өгнө | Утга |
|---|---|---|---|
| `work` | TA | анх ирсэн оюутан | Унтаж буй TA-г сэрээх |
| `started` | ирсэн оюутан | TA | Тусламж эхэлсэн |
| `called[i]` | сандал дээрх оюутан i | TA | Ээлж ирлээ |
| `done[i]` | тусламж авч буй оюутан i | TA | Тусламж дууслаа |
| `returned` | TA | оюутан i | Оюутан программчлалдаа буцлаа |
| `ticks[i]`, `ta_tick`, `ack` | worker | удирдагч | 100 мс-ийн загварын цаг |

Оюутны төлөв: **программчлах → (сандал дээр хүлээх) → тусламж авах → программчлах**.
TA-ийн төлөв: **унтах → туслах → дараагийнхад туслах эсвэл унтах**. Дараалал нь 40 элементийн
массив, бодит хязгаар нь сандлын тоо (≤ 20).

## 5. Хэрэгжилт

### 5.1 Оюутан ба TA

```text
student i:                                  TA:
  loop                                        loop
    wait ticks[i]          (программчлах)       wait work               (унтах)
    lock mu                                      lock; begin_help(current); unlock
    if now >= due[i]:  arrive                    post started
      TA сул   -> current = i                    loop every tick
      сул сандал -> queue.push(i)                  lock; remaining--; unlock
      эс бөгөөс -> full_return, due = now+r        if remaining == 0:
    unlock                                           post done[current]; wait returned
    TA сул:     post work; wait started              lock
    post ack                                         queue хоосон биш -> next = queue.pop
    сандалд суусан: wait called[i]                                       begin_help(next)
    wait done[i]           (тусламж)                 эс бөгөөс -> current = -1 (унтах)
    lock; state = программчлах; due = now+r          unlock; post called[next]
    unlock; post returned                          post ack
```

Mutex-ийг бүх хамтын өгөгдлийн өөрчлөлтөд барьж, `sem_wait`, `sem_post`-оос өмнө суллана.

### 5.2 Загварын цаг ба хоёр горим

`sim_step()` нь нэг tick (100 мс): `now++`, TA туслаж байвал `ta_tick` өгч `ack`-ийг хүлээнэ,
дараа нь программчилж буй оюутнуудад `ticks[i]` өгнө. Сандал дээрх болон тусламж авч буй
оюутан tick авахгүй — тэд `called[i]`, `done[i]` дээр блоклогдсон байна.

- **Seed горим:** оюутнуудыг нэг нэгээр нь ажиллуулж `ack` хүлээнэ. Үр дүн seed-ээр яг давтагдана.
- **Чөлөөт горим:** бүх программчилж буй оюутанд зэрэг `ticks[i]` өгч, дараа нь бүх `ack`-ийг
  хүлээнэ. Оюутнууд TA, сандал, mutex-ийн төлөө бодитоор өрсөлдөнө.

### 5.3 Тусламжийн шударга хуваарилалт

Оюутнуудын tick авах дарааллыг tick бүр seed-тэй тусдаа LCG-ээр Fisher–Yates аргаар холино.
Хувилбар 1.0 тогтмол `(k + now) % n` дараалал ашигладаг байсан тул TA сулрах tick нь
тусламжийн хугацааны алхмаар давтагдахад үргэлж ижил оюутнууд түрүүлдэг байв (8.3). Мөн LCG-ийн
сул доод битийн оронд дээд 16 битийг ашиглана.

### 5.4 Журнал, оролт, экспорт

`record_event` бүх үйл явдлыг түр файлд, сүүлийн 6-г UI-ийн буферт бичнэ. `Model.reset` нь
ctypes-д дамжуулахаас өмнө төрөл, хязгаар, min ≤ max-ийг шалгадаг (4294967297 → 1 болох
эрсдэлийг хаана); UI алдаатай талбарын нэр, хязгаарыг бичиж тухайн талбарыг сонгоно. CSV-г
түр файлд бичээд амжилттай бол `os.replace`-ээр сольж, файлын эрхийг хадгална. Нөөц
үүсгэхэд алдаа гарвал хэсэгчлэн үүссэн thread, semaphore-ийг цэвэрлэнэ.

### 5.5 UI

Автомат горим `time.monotonic()`-оор хугацааг хэмжиж, загварын цагийг бодит цаг × хурдтай
тэнцүү байлгана (зурах хугацаанаас үл хамаарна). Цонхны хэмжээ багасахад зөвхөн canvas
жижгэрч, тайлбар, төлөвийн мөр, лог үргэлж харагдана.

## 9. Хэлэлцүүлэг

**Сандал.** Сандал нэмэхэд буцалт буурч, TA-ийн ачаалал 71 %-иас 99.5 % хүртэл өсч, нэг
минутад туслах тоо 21-ээс 30 болно. Үнэ нь хүлээлт: 3 сандалтай үед дундаж 4.1 с. 6 оюутантай
үед 5 сандал = бүх боломжит хүлээгч тул буцалт 0. Иймээс сандал TA-ийн сул зогсолтыг хаана,
харин TA-ийн хүчин чадлаас (≈ 30 тусламж/мин) илүү гаргахгүй.

**Шударга байдал.** v1.0-ийн тогтмол дараалал Урт туршилтад 36 оюутныг огт тусламжгүй
орхисон нь номын бодлогын шинж биш, хэрэгжилтийн алдаа байв: 0 сандал, тогтмол хугацаатай үед үйлчлүүлэх
оюутны тоо яг n / gcd(n, тусламжийн tick) байсан. Санамсаргүй дарааллаар 37 / 40 болсон; үлдсэн 3 нь 101 с-д
100 тусламж 40 оюутанд санамсаргүй хуваарилагдсаны үр дүн (хүлээгдэх утга ≈ 37).

**Синхрончлол.** Seed горимд worker-ууд ээлжлэн ажилладаг тул mutex дээр өрсөлдөөн бараг
үүсдэггүй (0.01 %); энэ горим давтагдах, тайлбарлах зориулалттай. Чөлөөт горимд lock-ийн
20 % өрсөлдөж, mutex-ийг авахад TSan race илрүүлж дүрэм эхний tick-д эвдэрсэн нь mutex
шаардлагатайг, харин mutex-тэй үед 15 000 tick-д зөрчил гараагүй нь протокол зөв болохыг
харуулна.

**Хязгаарлалт.** (1) `sleep()`-ийн оронд загварын цаг: хугацаа tick-ийн нарийвчлалтай (0.1 с).
(2) Чөлөөт горимд ч tick-ийн хил дээр бүх worker зогсдог; tick дотор л зэрэг ажиллана.
(3) Сандалгүй буцсан оюутанд хугацааны баталгаа байхгүй. (4) Тоолуур `int`, API-г нэг
удирдах thread дуудна. (5) WSL2-д туршаагүй.

## 10. Дүгнэлт
